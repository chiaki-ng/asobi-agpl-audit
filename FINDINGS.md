## Measured evidence

**The developer's statements.** On [chiaki-ng issue #725](https://github.com/chiaki-ng/chiaki-ng/issues/725) (March 25–26, 2026), the developer wrote ([dated comment snapshot](evidence/developer-statements-issue-725.json)): “I'm not using any Chiaki code”; “All these steps can be found just as fine via the Windows remote play client where I got most of my info from”; and “My implementation is written entirely in Swift, no Chiaki or PSStream code is compiled, linked, or included.”

His own shipped code contradicts these statements:

1. **His bundled notes.** Releases 1.0–1.3 ship developer notes describing Asobi as “a pure Swift version of Chiaki's PlayStation Remote Play streaming protocol”. That includes builds packaged after the public denial. The notes were deleted in 1.3.1 (about April 30). The same five notes are byte-identical in all 20 store releases from 1.0 to 1.3, and Apple's code signature seals each one: the signature covers `_CodeSignature/CodeResources`, which lists every note's SHA-256 ([seal check and quoted lines](evidence/developer-notes.json)). They also cite Chiaki source by file and line, for example “Based on Chiaki `takion.c` (lines 175-660)”, and one is titled “Takion Protocol Implementation - Fixes Based on Chiaki Source”.
2. **His log messages cite chiaki-ng source by file and line.** Releases 1.1–1.1.8 log messages such as “DATA ACCEPT exchange (Chiaki holepunch.c:1507-1556)”. These ranges match only chiaki-ng v1.9.7–v1.9.9. They come from neither psn-api nor Sony's client.
3. **The references were removed, but the implementation stayed.** Release 1.1.9, packaged about a day after the GitHub denial, changed 36 log messages: 34 lost the word “Chiaki” and 2 lost “PSStream”, mostly by deleting only that word. Release 1.2 removed the last two PSStream references. In 1.4.2 a `CHIAKI` constant was removed, and the developer's own server API parameter `chiakiId` was renamed `encodedId` ([all removals](evidence/removals.json)). The chiaki-ng-derived implementation remains in the current release, 1.5.
4. **Neither Sony client contains the chiaki-ng choices Asobi carries.** This includes the Windows client he named as his main source. See the comparison below. Sony's macOS client 9.5.0 also lacks every Chiaki marker checked ([scan](evidence/sony-mac-client.json)).
5. **The Android app ships the same Chiaki-derived design, in C++.** Every Android build examined (1.0.3, 1.0.7, 1.1.1; one signing certificate) has a native C++ library, `libasobidroid.so`, exporting `asobi::TakionConnection`, `asobi::RPCrypt::aeropause_*` and `asobi::GKCrypt::counter_add`, named after Chiaki's functions. From the earliest build it carries my own chiaki-ng code in four places: the 2023 key-position arithmetic; the RUDP counter and header seed (`random % 0x5C01 + 0x1FF`, `random + 0x8000`); candidate selection exported as `Holepuncher::SELECT_CANDIDATE_TRIES` = 20 and run as up to 20 rounds of 500 ms, as in my `check_candidates`; and my random-allocation method exported as `RANDOM_ALLOCATION_SOCKETS` = 250, which opens 250 `SO_REUSEPORT` sockets and is renamed “birthday attack” in its logs. It also embeds Chiaki's launch-spec template with only the MTU and RTT values changed, and a `CHIAKI` string before Chiaki's client-disconnect message until 1.1.1, as on iOS until 1.4.2 ([comparison](evidence/rudp-holepunch-comparison.json)). The iOS app has the same RUDP seed and 250-socket count. No package contains an AGPL notice, Chiaki attribution or source link ([Android measurements](evidence/android.json)). That contradicts the statement that Asobi is written entirely in Swift, and the same design on two platforms points to one Chiaki-derived codebase.

These are documented contradictions between the developer's statements and his shipped code. No claim about motive is made.

The audit covers 29 examined historical iOS releases from 1.0 through 1.4.3, with gaps explicitly retained, plus separately measured iOS 1.5. The historical analysis packages passed the recorded identity, resource and selected-region comparisons against matching original Apple packages. This supports association but does not independently authenticate every instruction or verify Apple signatures.

Bundled developer notes describe a Swift implementation based on Chiaki. Examined 1.1–1.1.8 releases contain four exact chiaki-ng source-range citations. Per-line history separates my contributions from other authors' work. Actual ACCEPT/RESULT and CTRL operation families have been recovered, with relevant behavior traced through citation removal in 1.1.9 and into 1.5. Compiled message layouts, cancellation, ACK handling and current validation/crypto paths are documented. Counter order, error handling and receive architecture differ from the cited C; a complete protected-expression translation of every cited block is not established.

The 2023 key-position adjustment and 2024 STUN-list choice associated with my commits corroborate later-fork provenance. A 1.5 key-update function has four direct call sites from one containing function. Names, protocol constants, URLs and an arithmetic expression alone are not the protected works claimed. The six earlier releases newly examined on October 7 preserve Chiaki-labelled code and notes but do not move the observed later citations/key-position pattern or PSStream markers before 1.1.

## Contrary evidence and unresolved questions

To separate protocol requirements from chiaki-ng’s own implementation choices, I analyzed both of Sony’s official PS Remote Play clients: iOS 9.5.0, and Windows 9.5.0.08040, the client the developer named as his main source. Both do NAT traversal through Sony’s own NP signaling library and use Sony’s own STUN host (stun.playstation.net). The iOS client tracks key position with a keystream ring buffer. Asobi uses none of these Sony mechanisms. It instead carries the following chiaki-ng-specific choices, which neither Sony client has:

| Implementation choice | chiaki-ng | Sony PS Remote Play (iOS and Windows) | Asobi |
| --- | --- | --- | --- |
| STUN hosts fetched from the always-online-stun GitHub list (my 2024 change) | Yes | No | From 1.1.5; still in 1.5 |
| Port increment derived from three STUN responses by address pattern: A/A/B, A/B/A, A/B/B and same-address unequal increments, with the same formula in each case (my code) | Yes | No | From 1.1.8; still in 1.5 |
| 75 port guesses on random NAT allocation; 8 predicted guesses otherwise (my code) | Yes | No | From 1.1 / 1.1.3 |
| Key position advanced by size + size % 16 (my 2023 change) | Yes | No (iOS: ring-buffer design, pattern absent; Windows: no match by heuristic) | Yes, including 1.5 |
| Hard-coded public STUN list led by stun.moonlight-stream.org, then Google stun–stun4 (chiaki-ng, another author) | Yes | No | From 1.0 |

The PSN session messages (OFFER/ACCEPT/RESULT) appear in all three and are treated as protocol, not claimed. The matched choices are not required to interoperate, since Sony’s client works without them. They therefore indicate derivation from chiaki-ng rather than from the protocol or Sony’s app. Individual constants and URLs are offered as evidence of copying, not as independently protected expression. The port-allocation decision structure is offered as both.

The developer's March account ([blog, March 29, 2026](https://asobiapp.com/blog/2026-03-29-week-14/)) says private code inspection was offered, which I acknowledge. It also describes my closing of the issue as validation that no Chiaki code was used; I closed it relying on his assurance, before the evidence above was collected. In a [July 19, 2026 post](https://asobiapp.com/blog/2026-07-19-edition-20-week-30-the-411/) he again claims an independent implementation and discusses avoiding Chiaki's AGPL obligations. A private inspection offer is not by itself a demonstrated recipient source-delivery mechanism, and an inspection of the current code alone would not show what the earlier releases contained.

The audit also tested whether Asobi copied Pylux, Forward Technologies' AGPL source, after it was published. It found no Pylux-specific string that first appears in Asobi after 2026-05-08 ([negative result](evidence/pylux-check.json)), so no copying from Pylux is claimed. Forward Technologies' claim rests on the earlier PSStream build.

October 6 checks of the supplied 1.5 About/legal views and inspected publisher pages found no visible Chiaki/AGPL acknowledgement or corresponding-source access. The About screen shows 1.5 without a build number. These are bounded historical observations, not absence from every screen or channel. PSStream/Pylux is a separately identified authorized rights-holder claim in this Asobi case; PSStream's January 14, 2026 Steam build (2.9.8) already contains the step numbering and three authored log lines carried from 1.1 through 1.5; eight more selected lines appear by Asobi 1.1.5 and all eleven persist in 1.5, so the order no longer depends on Pylux's later source ([measurement](evidence/psstream-steam-build.json)). This is evidence of modelled wording and flow, not a measurement of translated source expression. An extracted official Sony PlayStation Plus PC client has none of the eleven selected lines or checked step markers as exact ASCII in 140 files, but does contain all eight compared identifier names; those names are excluded from the PSStream-specific inference. This PC app streams PS4/classic titles, so it is an imperfect control for PS5 cloud streaming. The authorized rights holders are identified below and in RIGHTS-HOLDERS.md; the technical limitations still apply to each claim.

Full protected-expression comparison, complete combined-work scope, actual source delivery and separate permission remain unresolved. No app execution or source rebuild was performed. A source request, Apple complaint or GitHub update has not been sent by this preparation.
